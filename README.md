# خدمة التربية الكنسية

منصة إدارة عملية لخدمة التربية الكنسية بكنيسة رئيس الملائكة الجليل ميخائيل بدمنهور — تسجيل حضور وغياب، متابعة افتقاد، تقويم أعياد ميلاد، وإدارة الهيكل التنظيمي للخدمة ومخدوميها، بهوية بصرية قبطية أرثوذكسية حديثة وواجهة عربية RTL كاملة.

## التشغيل محليًا

**المتطلبات:** Node.js 20+ و npm.

```bash
npm install     # تثبيت الحزم (يشغّل prisma generate تلقائيًا)
npm run setup   # ينشئ .env بمفتاح عشوائي + يطبّق الترحيلات + يهيّئ الهيكل التنظيمي
npm run dev     # يعمل على http://localhost:3000
```

للبناء الإنتاجي: `npm run build` ثم `npm start`.

أوامر مساعدة أخرى:

```bash
npm run db:studio   # واجهة Prisma Studio لمعاينة/تعديل قاعدة البيانات
npm run lint         # ESLint
```

## الحساب الأول (بعد التهيئة)

التهيئة تُنشئ **حساب المسؤول وحده** مع الهيكل التنظيمي الكامل. باقي الحسابات
يُنشئها المسؤول من داخل النظام (الإعدادات ← المستخدمون).

| الدور | اسم المستخدم | كلمة المرور |
|---|---|---|
| مسؤول النظام | `admin` | `Elmalak@123` |

⚠️ **غيّر كلمة المرور فورًا بعد أول دخول** — فهي منشورة في هذا الملف ومتاحة لأي أحد.

## البنية والصلاحيات

### الهيكل التنظيمي

```
Service ........... خدمة التربية الكنسية
 └─ Stage ......... حضانة / ابتدائي / إعدادي / ثانوي
     └─ Division .. بنين / بنات   (الحضانة: قسم واحد غير مُقسّم بالنوع)
         └─ Grade . الصف الأول … + اسم أسرة الفصل (يسجّله أمين المرحلة)
             └─ Enrollment (قيد المخدوم في صف خلال سنة دراسية)
                 └─ Child (بياناته الشخصية وأرقام تليفوناته)
```

المخدوم مرتبط بالصف عبر **قيد (Enrollment)** مربوط بسنة دراسية، وليس ارتباطًا
مباشرًا: الترفيع للصف التالي = قيد جديد، فيبقى سجل الحضور القديم منسوبًا
للصف الذي كان فيه فعلًا. والحضور والافتقاد مرتبطان بالقيد لا بالمخدوم.

### الدور ≠ التكليف

الدور يحدد **ماذا يستطيع المستخدم أن يفعل**، والتكليف يحدد **أين**:

| الدور | ماذا يفعل |
|---|---|
| `ADMIN` | كل شيء: إدارة الحسابات والهيكل التنظيمي |
| `SERVICE_SECRETARY` | كل ما في نطاقه داخل الخدمة |
| `STAGE_SECRETARY` | نطاقه + تسمية أسر الفصول التابعة له |
| `SERVANT` | الحضور والافتقاد وبيانات المخدومين في نطاقه |

التكليف (`Assignment`) صفٌّ منفصل يربط المستخدم بمستوى واحد من الهيكل
(خدمة أو مرحلة أو قسم أو صف)، و**يمكن أن يكون للمستخدم أكثر من تكليف**. أمثلة:

| المستخدم | الدور | التكليف |
|---|---|---|
| أمين الخدمة | `SERVICE_SECRETARY` | الخدمة كلها |
| أمين مرحلة ابتدائي بنين | `STAGE_SECRETARY` | ابتدائي › بنين |
| خادم الصف الثالث | `SERVANT` | إعدادي › بنين › الصف الثالث |

«أمين/أمينة» و«خادم/خادمة» ليسا دورين منفصلين: المسمّى يُصاغ من الدور + حقل
النوع (`gender`) في حساب المستخدم، والقسم المكلَّف به يحدد بنين أم بنات.

### كيف تُطبَّق الصلاحيات

الدالة `resolveScope(user)` في `src/lib/scope.ts` تترجم (الدور + التكليفات)
إلى **قائمة الصفوف** التي يراها المستخدم، وهي نقطة الحقيقة الوحيدة:

- كل استعلام في `src/lib/queries.ts` يُصفّي بها **داخل الدالة نفسها**.
- كل تعديل في `src/actions/` يستدعي `assertGradeAccess` أو `assertEnrollmentAccess` قبل الكتابة.

فلا يعتمد الأمان على تذكّر كاتب الصفحة أن يفحص: طلبٌ مباشر لصف خارج النطاق
(حتى بكتابة الرابط يدويًا) يُرفض من نفس الدالة التي تجلب البيانات.

**المستخدم لا ينشئ حسابًا لنفسه ولا يغيّر دوره أو نطاقه** — لا يوجد مسار
تسجيل ذاتي في النظام أصلًا؛ المسؤول وحده ينشئ الحسابات ويحدد الأدوار والتكليفات.

## متغيرات البيئة

انظر `.env.example`:

- `DATABASE_URL` — رابط قاعدة بيانات PostgreSQL.
- `AUTH_SECRET` — مفتاح توقيع جلسات الدخول؛ **يجب** أن يكون طويلًا وعشوائيًا وسريًا في الإنتاج (لن يعمل التطبيق بدونه).

## النشر على Vercel

المشروع جاهز للنشر على Vercel، لكنه يحتاج قاعدة بيانات PostgreSQL مستضافة — **لا يمكن استخدام ملف قاعدة بيانات محلي على Vercel** لأن نظام الملفات هناك للقراءة فقط ومؤقت.

**١. أضف قاعدة بيانات**

من لوحة تحكم مشروعك على Vercel: تبويب **Storage** ← **Create Database** ← اختر **Neon** أو **Prisma Postgres** (كلاهما له خطة مجانية). بعد الربط يضيف Vercel متغيّر `DATABASE_URL` تلقائيًا للمشروع.

**٢. أضف مفتاح الجلسات**

من **Settings** ← **Environment Variables** أضف:

| المتغيّر | القيمة |
|---|---|
| `AUTH_SECRET` | نص عشوائي طويل — ولّده بـ `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |

**٣. أعد النشر**

من تبويب **Deployments** اضغط **Redeploy** على آخر نشر (مع إلغاء تفعيل خيار الكاش إن وُجد).

أمر البناء `npm run build` يطبّق ترحيلات قاعدة البيانات ويهيّئ الهيكل التنظيمي تلقائيًا في أول نشر، فلا حاجة لأي خطوة يدوية على قاعدة البيانات.

> ترحيلات Prisma تُنفَّذ عبر **الاتصال المباشر (unpooled)** ومع تعطيل قفل الترحيلات، لأن القفل لا يعمل عبر الـpooler وقد يتسرّب فيوقف كل نشرة تالية. التطبيق وقت التشغيل يظل على الاتصال المُجمَّع. يتكفّل `scripts/db-deploy.mjs` بذلك تلقائيًا — لا يحتاج أي إعداد إضافي.

> ⚠️ بعد أول دخول ناجح، **غيّر كلمة مرور حساب `admin` فورًا** من الإعدادات ← المستخدمون، لأنها منشورة في هذا الملف.

## الهوية البصرية واللوجوهات

اللوحة اللونية (`src/app/globals.css`) استُخرجت من رؤية اللوجوهين المرسَلين مباشرة (لوجو الكنيسة الذهبي/الكريمي بأيقونة رئيس الملائكة ميخائيل، ولوجو المطرانية الأسود بالصليب القبطي): ذهبي عتيق أساسي + أخضر عميق ثانوي + خلفية كريمية دافئة، مع وضع داكن كامل مصمَّم خصيصًا (وليس مجرد عكس ألوان).

**اللوجوهان المستخدمان في الواجهة هما اللوجوهان الأصليان للكنيسة والمطرانية**، بعد محو خلفيتيهما برمجيًا:

| الملف | المصدر | المعالجة |
|---|---|---|
| `public/logos/church-logo.png` | `assets/logos/church-logo-source.jpg` | محو الخلفية السوداء بـ flood fill من حدود الصورة (حتى لا تُمَس الأجزاء الداكنة داخل الأيقونة نفسها) + تنعيم الحافة لإزالة هالة ضغط JPEG |
| `public/logos/eparchy-logo.png` | `assets/logos/eparchy-logo-source.jpg` | تحويل درجة السواد إلى شفافية (alpha = darkness)، فتبقى الحروف القبطية وفراغاتها الداخلية سليمة على أي خلفية |

سكربت المعالجة في `scripts/remove-logo-background.py` (يحتاج `pip install Pillow numpy`)، والصور الأصلية باقية في `assets/logos/` للرجوع إليها.

لأن شعار المطرانية حبر أسود خالص، تُعكس ألوانه تلقائيًا إلى الأبيض في الوضع الداكن عبر القاعدة `.eparchy-mark` في `globals.css`.

المكوّنان `ChurchLogo` و`EparchyLogo` في `src/components/layout/` هما نقطة الاستخدام الوحيدة؛ لتحديث أي شعار لاحقًا استبدل ملف الـPNG فقط.

## حل المشكلات الشائعة

**بعد تسجيل الدخول يرجعني للصفحة نفسها / لا يفتح شيء**

كان هذا يحدث عند تشغيل نسخة الإنتاج والدخول عليها من عنوان غير `localhost` عبر HTTP عادي (مثل فتح الموقع من الموبايل على `http://192.168.x.x:3000`): كان كوكي الجلسة يُرسَل بخاصية `Secure` فيرفضه المتصفح على اتصال غير مشفّر، فتضيع الجلسة ويعود المستخدم لصفحة الدخول. **تم إصلاحه** — صار التطبيق يضبط `Secure` حسب بروتوكول الطلب الفعلي (`x-forwarded-proto`)، فيعمل على HTTP داخل الشبكة المحلية وعلى HTTPS في الإنتاج.

**«تعذّر تشغيل التطبيق» على الموقع المنشور**

معناها أن `DATABASE_URL` أو `AUTH_SECRET` غير مضبوط في بيئة النشر، أو أن قاعدة البيانات غير متاحة. راجع قسم [النشر على Vercel](#النشر-على-vercel) أعلاه. (كان السبب الأصلي هو محاولة استخدام SQLite كملف على القرص، وهو ما لا يعمل على Vercel إطلاقًا — وقد تم تحويل المشروع إلى PostgreSQL.)

**شاشة بيضاء أو خطأ عند فتح أي صفحة بعد استنساخ المشروع**

ملف `.env` غير مرفوع مع المستودع (لأنه يحتوي أسرارًا)، فبدونه لا يعمل التطبيق. شغّل:

```bash
npm run setup
```

يُنشئ `.env` بمفتاح `AUTH_SECRET` عشوائي، يطبّق ترحيلات قاعدة البيانات، ويعبّئ البيانات الأولية (يتخطى الموجود مسبقًا). التطبيق الآن يعرض رسالة خطأ عربية واضحة بدل الشاشة البيضاء إن نقص أي إعداد.

**تسجيل الدخول يرفض البيانات الصحيحة** — قاعدة البيانات غالبًا فارغة؛ شغّل `npm run db:seed`.

**فشل النشر بـ`P1002: Timed out trying to acquire a postgres advisory lock`**

قفل الترحيلات (`pg_advisory_lock`) لا يعمل عبر اتصال Neon المُجمَّع، بل **يتسرّب**: ينتهي انتظار العميل بعد عشر ثوانٍ بينما يبقى خادم خلفي في الـpooler ماسكًا للقفل، فتفشل كل محاولة تالية حتى على الاتصال المباشر.

تم إصلاحه في `scripts/db-deploy.mjs`: الترحيلات تمر على الاتصال المباشر **ومع تعطيل القفل** (`PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK`). القفل وظيفته منع تزامن عمليتي ترحيل، وهو تزامن لا يحدث هنا لأن Vercel ينفّذ بناءً واحدًا في المرة.

**فشل النشر بـ`type "Role" already exists` أو `P3018`**

قاعدة البيانات تحتوي جداول من ترحيل قديم لم يعد موجودًا. إن لم تكن بها بيانات حقيقية بعد، أفرغها من محرر SQL في Neon ثم أعد النشر:

```sql
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
```

⚠️ هذا يمسح كل شيء — لا تستخدمه بعد أن تبدأ الخدمة في إدخال بياناتها الفعلية.

## القرارات التصميمية ولماذا

عند تعارض متطلبين اخترت الحل الأكثر عمليةً وأمانًا وقابلية للصيانة:

- **PostgreSQL مستضافة بدل SQLite:** بدأ المشروع بـSQLite لبساطتها، لكن النشر على Vercel أثبت أنها غير صالحة هناك: نظام الملفات للقراءة فقط ومؤقت، وكل طلب قد يعمل على خادم مختلف، فلا تُحفظ أي كتابة. PostgreSQL المستضافة هي الخيار الصحيح لأي نشر سحابي.
- **تشغيل الترحيلات والتعبئة الأولية داخل أمر البناء:** (`prisma migrate deploy && prisma db seed && next build`) حتى لا تحتاج خطوة يدوية بعد كل نشر. التعبئة محميّة بشرط: تعمل فقط إذا كانت قاعدة البيانات فارغة تمامًا، فلا تُعيد إنشاء بيانات حذفها الخدام لاحقًا.
- **مصادقة مخصّصة بدل NextAuth:** النسخة المتوافقة مع React 19 من NextAuth كانت تُفشل تثبيت الحزم (عطل معروف في محلل تبعيات npm مع هذا الإصدار)؛ حل JWT+كوكي httpOnly مباشر أبسط وأكثر قابلية للتتبع لتطبيق بحجم كهذا، مع نفس ضمانات الأمان (تواقيع موقّعة، httpOnly، secure في الإنتاج).
- **Server Actions بدل REST API منفصل:** يقلّل الكود المكرر (لا حاجة لـ fetch + API route لكل نموذج) مع إبقاء كل التحقق (`zod`) وفحص الصلاحيات على الخادم دائمًا.
- **جلسات الحضور اليومية + الافتقاد الشهري:** يعكس تمامًا الجدولين الفعليين في ملف بيانات الخدمة المرفق (شبكة شهرية للحضور بعدة أعمدة لكل شهر، وعمود واحد شهري للافتقاد).

## ما هو منفَّذ فعليًا

لا توجد شاشات "قريبًا" في هذا المشروع — كل ما يظهر في الواجهة يعمل فعليًا ومتصل بقاعدة بيانات حقيقية:

- تسجيل دخول/خروج بجلسات موقَّعة وحماية كل المسارات.
- صلاحيات ثلاثية الأدوار مطبَّقة في السيرفر (وليس فقط في الواجهة).
- إدارة كاملة (إضافة/تعديل/حذف/تعطيل) للمراحل، الأسر، المخدومين، أرقام تليفوناتهم المتعددة، والمستخدمين.
- تسجيل حضور فعلي لكل جلسة بثلاث حالات (حاضر/غائب/بعذر) مع تنقل بين التواريخ وسجل جلسات سابقة.
- متابعة افتقاد شهرية فعلية مع ملاحظات لكل مخدوم.
- تقويم أعياد ميلاد حقيقي مبني على بيانات المخدومين الفعلية، مع تمييز الشهر الحالي واليوم نفسه.
- لوحة تحكم بإحصائيات حقيقية (لا بيانات وهمية): عدد الأسر/المخدومين، نسبة الحضور والافتقاد الفعلية هذا الشهر، آخر النشاطات، أقرب أعياد الميلاد.
- بحث فوري، حالات فارغة/تحميل/خطأ مصمَّمة لكل شاشة بيانات.
- وضع داكن كامل مصمَّم خصيصًا (ليس عكس ألوان).
- Responsive حقيقي من 360px إلى الشاشات الكبيرة: جداول تتحول لبطاقات على الهاتف، تنقل سفلي على الهاتف وشريط جانبي على الشاشات الكبيرة.

تم اختبار كل هذه التدفقات فعليًا عبر متصفح Chromium حقيقي (Playwright) على أبعاد سطح المكتب والهاتف، بثلاثة أدوار مختلفة، بدون أي أخطاء في الـ console.
