# خدمة التربية الكنسية

منصة إدارة عملية لخدمة التربية الكنسية بكنيسة رئيس الملائكة الجليل ميخائيل بدمنهور — تسجيل حضور وغياب، متابعة افتقاد، تقويم أعياد ميلاد، استيراد كشوف المخدومين من ملفات جاهزة، وإدارة الهيكل التنظيمي للخدمة ومخدوميها، بهوية بصرية قبطية أرثوذكسية حديثة وواجهة عربية RTL كاملة.

## التشغيل محليًا

**المتطلبات:** Node.js 20+ و npm.

```bash
npm install     # تثبيت الحزم (يشغّل prisma generate تلقائيًا)
npm run setup   # ينشئ .env بمفتاح عشوائي + يطبّق الترحيلات + يهيّئ الهيكل التنظيمي
npm run dev     # يعمل على http://localhost:3000
```

للبناء الإنتاجي: `npm run build` ثم `npm start`.

أوامر مساعدة أخرى:

```bash
npm run db:studio   # واجهة Prisma Studio لمعاينة/تعديل قاعدة البيانات
npm run lint         # ESLint
```

## الحساب الأول (بعد التهيئة)

التهيئة تُنشئ **حساب المسؤول وحده** مع الهيكل التنظيمي الكامل. باقي الحسابات
يُنشئها المسؤول من داخل النظام (الإعدادات ← المستخدمون).

| الدور | اسم المستخدم | كلمة المرور |
|---|---|---|
| مسؤول النظام | `admin` | `Elmalak@123` |

⚠️ **غيّر كلمة المرور فورًا بعد أول دخول** — فهي منشورة في هذا الملف ومتاحة لأي أحد.

## البنية التقنية

| الطبقة | الاختيار | السبب |
|---|---|---|
| إطار العمل | Next.js 16 (App Router) + TypeScript | Server Components + Server Actions تقلّل الكود المكرر وتبقي التحقق والصلاحيات على السيرفر |
| التصميم | Tailwind CSS v4 (Design tokens في `globals.css`) | نظام تصميم حقيقي عبر متغيرات CSS، ويدعم الوضع الداكن دون تكرار |
| قاعدة البيانات | PostgreSQL عبر Prisma ORM | تعمل على الاستضافات السحابية (Vercel وغيرها) التي لا توفّر تخزينًا دائمًا على القرص، وتتحمّل استخدام عدة خدام في وقت واحد |
| المصادقة | جلسة JWT موقّعة (مكتبة `jose`) في كوكي httpOnly + `bcryptjs` لتجزئة كلمات المرور | حل خفيف مباشر بديل عن NextAuth (الإصدار المتوافق مع React 19 كان يسبب عطل معروف في محلل تبعيات npm وقت البناء) |
| الأيقونات | lucide-react | نظام أيقونات واحد متسق |
| الحركة | CSS transitions/keyframes + تفاعلات مدروسة | حركة خفيفة بدون مكتبات ثقيلة |
| الخط | Cairo (عبر `next/font/google`) | خط عربي حديث بعائلة أوزان كاملة، ويدعم اللاتينية أيضًا |

## البنية والصلاحيات

### الهيكل التنظيمي

```
Service ........... خدمة التربية الكنسية
 └─ Stage ......... حضانة / ابتدائي / إعدادي / ثانوي
     └─ Division .. بنين / بنات   (الحضانة: قسم واحد غير مُقسّم بالنوع)
         └─ Grade . الصف الأول … + اسم أسرة الفصل (يسجّله أمين المرحلة)
             └─ Enrollment (قيد المخدوم في صف خلال سنة دراسية)
                 └─ Child (بياناته الشخصية وأرقام تليفوناته)
```

المخدوم مرتبط بالصف عبر **قيد (Enrollment)** مربوط بسنة دراسية، وليس ارتباطًا
مباشرًا: الترفيع للصف التالي = قيد جديد، فيبقى سجل الحضور القديم منسوبًا
للصف الذي كان فيه فعلًا. والحضور والافتقاد مرتبطان بالقيد لا بالمخدوم.

### الدور ≠ التكليف

الدور يحدد **ماذا يستطيع المستخدم أن يفعل**، والتكليف يحدد **أين**:

| الدور | ماذا يفعل |
|---|---|
| `ADMIN` | كل شيء: إدارة الحسابات والهيكل التنظيمي |
| `SERVICE_SECRETARY` | كل ما في نطاقه داخل الخدمة |
| `STAGE_SECRETARY` | نطاقه + تسمية أسر الفصول التابعة له |
| `SERVANT` | الحضور والافتقاد وبيانات المخدومين في نطاقه |

التكليف (`Assignment`) صفٌّ منفصل يربط المستخدم بمستوى واحد من الهيكل
(خدمة أو مرحلة أو قسم أو صف)، و**يمكن أن يكون للمستخدم أكثر من تكليف**. أمثلة:

| المستخدم | الدور | التكليف |
|---|---|---|
| أمين الخدمة | `SERVICE_SECRETARY` | الخدمة كلها |
| أمين مرحلة ابتدائي بنين | `STAGE_SECRETARY` | ابتدائي › بنين |
| خادم الصف الثالث | `SERVANT` | إعدادي › بنين › الصف الثالث |

«أمين/أمينة» و«خادم/خادمة» ليسا دورين منفصلين: المسمّى يُصاغ من الدور + حقل
النوع (`gender`) في حساب المستخدم، والقسم المكلَّف به يحدد بنين أم بنات.

### كيف تُطبَّق الصلاحيات

الدالة `resolveScope(user)` في `src/lib/scope.ts` تترجم (الدور + التكليفات)
إلى **قائمة الصفوف** التي يراها المستخدم، وهي نقطة الحقيقة الوحيدة:

- كل استعلام في `src/lib/queries.ts` يُصفّي بها **داخل الدالة نفسها**.
- كل تعديل في `src/actions/` يستدعي `assertGradeAccess` أو `assertEnrollmentAccess` قبل الكتابة.

فلا يعتمد الأمان على تذكّر كاتب الصفحة أن يفحص: طلبٌ مباشر لصف خارج النطاق
(حتى بكتابة الرابط يدويًا) يُرفض من نفس الدالة التي تجلب البيانات.

**المستخدم لا ينشئ حسابًا لنفسه ولا يغيّر دوره أو نطاقه** — لا يوجد مسار
تسجيل ذاتي في النظام أصلًا؛ المسؤول وحده ينشئ الحسابات ويحدد الأدوار والتكليفات.

## استيراد كشوف المخدومين

بدل إدخال عشرات الأسماء يدويًا، صفحة **«استيراد كشف»** ترفع الكشف كما هو وتحوّله
إلى مخدومين. المسار واحد مهما كانت الصيغة:

```
اختر الصف  →  ارفع الملف  →  يُقرأ ويُطابَق  →  جدول مراجعة قابل للتعديل  →  حفظ
```

**لا يُحفظ سطر لم يمر على جدول المراجعة.** هذه ليست خطوة شكلية: القراءة من
الملفات المصوَّرة تقريبية، وغلطة في رقم تليفون مخدوم مشكلة حقيقية.

### الصيغ الثلاث ودقّة كلٍّ منها

| الصيغة | أين تُقرأ | الدقّة |
|---|---|---|
| `.xlsx` `.csv` `.tsv` `.txt` | الخادم | كاملة |
| `.docx` وملفات PDF المكتوبة | الخادم / المتصفّح | عالية — يُعاد بناء الجدول من مواضع النص |
| PDF ممسوح ضوئيًا وصور `.png` `.jpg` … | المتصفّح (OCR) | تقريبية — راجع كل سطر |

ملفات PDF والصور **لا تُرفع إلى الخادم أصلًا**؛ يقرؤها المتصفّح ثم يرسل النص
المستخرَج وحده. ثلاثة مكاسب: كشف المخدومين لا يغادر جهاز صاحبه، والملفات الكبيرة
لا تصطدم بحدّ حجم الطلب في النشر بلا خادم، وقراءة صفحة ضوئيًا (عشرات الثواني)
لا تصطدم بمهلة الدوال.

محرّك القراءة الضوئية (Tesseract) وبيانات اللغة العربية مستضافة من الموقع نفسه
تحت `public/ocr` — لا من شبكة توزيع خارجية. ملفات المحرّك تُنسخ من `node_modules`
عند كل بناء (`scripts/prepare-ocr.mjs`) فلا تُحفظ في المستودع؛ أمّا
`ara.traineddata` فمحفوظ لأنه ليس جزءًا من أي حزمة.

### كيف يُقرأ جدول من ملف PDF

ملف PDF لا يحتوي «جدولًا»، بل نصًّا بإحداثيات. فيُعاد بناء الجدول على أربع خطوات
(‎src/lib/import/layout.ts‎)، وهي نفسها المستعملة مع ناتج القراءة الضوئية:

1. **سطور** — العناصر المتقاربة رأسيًا سطرٌ واحد.
2. **خلايا** — الفجوة داخل السطر تفصل عمودًا. والفروق قياسية لا تخمينية: القطع
   داخل الكلمة فراغه صفر، والمسافة بين كلمتين عُشر ارتفاع السطر، والفاصل بين
   عمودين أضعافه.
3. **أعمدة** — من مواضع خلايا صف العناوين نفسه، تمامًا كما يقرأ الإنسان الجدول.
   (وإن لم يُعثر على صف عناوين، تُستنبط الأعمدة من المساحات الرأسية الفارغة.)
4. **سجلات** — المخدوم الواحد يشغل عدة سطور: العنوان يلتفّ، وتليفونات الأب والأم
   والبيت تتراصّ، ورقمه المسلسل يتوسّط خانته. فيُتّخذ سطر الاسم مرساةً ويُضمّ إليه
   كل سطر هو أقرب ما يكون إليه.

وبعد القراءة:

- **الأسماء المتكرّرة تُدمج.** الكشف الواحد يجمع عادةً صفحة البيانات وصفحات
  الحضور والافتقاد، فيتكرّر الاسم في كل صفحة ولا تحمل بياناته إلا صفحة واحدة.
  تُجمع المواضع في سجل واحد، وإن اختلفت قيمتان للاسم نفسه ظهر تحذير بهما.
- **ما ليس اسمًا يُستبعد:** الآيات في صدر الصفحات، وأسماء الشهور في جداول
  الافتقاد، وصف العناوين المتكرّر أعلى كل صفحة، وسطور الإجمالي.
- **صاحب كل رقم يُقرأ ممّا يسبقه** لا من أول اسم في الخانة: «الأب: الأم: ٠١٢…»
  رقمٌ للأم تُرك مكان رقم الأب فارغًا. والأسماء غير المعتادة («الخال») تُؤخذ كما
  كُتبت بدل أن يُنسب الرقم خطأً.

#### عيب «لام ألف» في بعض ملفات PDF

بعض مولّدات PDF (ومنها PDFium الذي تستعمله متصفّحات كثيرة عند «الطباعة إلى PDF»)
تكتب رابطة **«لا»** بحرفيها مقلوبين، فيخرج «الاسم» من الملف «االسم»، و«الميلاد»
«الميالد»، و«علاء» «عالء».

القلب **لا يمكن ردّه آليًا**: «المالك» قد تكون «الملاك» وقد تكون على حالها، ولا
يفصل بينهما إلا المعنى. فالتعامل معه على وجهين:

- **العناوين تُصحَّح تلقائيًا** — توحيد ترتيب الحرفين عند المقارنة يكفي ليتطابق
  «االسم» مع «الاسم»، فتُقرأ أعمدة الملف كاملة.
- **الأسماء يُنبَّه عليها** — إن خلا الملف من «لا» تمامًا رغم طول نصّه العربي (وهو
  دليل قاطع على العيب)، يظهر تنبيه في أعلى المراجعة، ويوضع تحذير على كل اسم يُشتبه
  فيه ليصحّحه صاحب الكشف بنفسه.

### القالب: الطريق الذي لا يحتمل الخطأ

من داخل الصفحة: **«نزّل القالب الجاهز»**. ملف Excel يُبنى لكل مستخدم على حدة:

- العناوين مكتوبة بالضبط كما يتوقّعها القارئ.
- **الصف** و**النوع** و**صاحب التليفون** قوائم منسدلة لا تقبل غيرها — والقائمة
  لا تحوي إلا صفوف هذا المستخدم.
- عمود تاريخ الميلاد منسّق كتاريخ، وورقة «تعليمات» تشرح كل عمود.

فالملف يُملأ بالاختيار لا بالكتابة، ويصل مفهومًا من أول مرة.

### تحويل كشف ورقي إلى ملف جاهز

حين يكون الكشف ورقيًا أو بخط اليد — وهي الحالة التي لا تُجيدها القراءة الضوئية —
تُحوَّل بياناته مرة واحدة إلى ملف مطابق للقالب:

```bash
npm run make:import-file -- rows.json كشف-جاهز.xlsx
```

`rows.json` مصفوفة كائنات، مفاتيحها إمّا عناوين القالب العربية أو أسماء الحقول
الإنجليزية:

```json
{
  "grades": ["إعدادي › بنين › الصف الأول"],
  "rows": [
    { "الاسم": "أنطونيوس مجدي", "تاريخ الميلاد": "١٤/٩/٢٠١١", "الموبايل": "01000111222" },
    { "fullName": "ڤيرينا عماد", "birthDate": "2010-06-30", "gender": "أنثى" }
  ]
}
```

الأداة تستعمل **نفس** تعريف الأعمدة ونفس محلّلات القيم التي يستعملها الموقع عند
القراءة، فما تقبله يقبله الموقع بالضرورة. وما لا تفهمه تُبلّغ عنه قبل التسليم:

```
✓ 3 مخدومًا في كشف-جاهز.xlsx
⚠ 2 ملاحظة تحتاج مراجعة قبل التسليم:
  • سطر 3: تاريخ «غير معروف» غير مفهوم — تُرك فارغًا
  • سطر 4: بلا اسم — أُسقط
```

### ما يفعله الاستيراد وما لا يفعله

- **الصف**: يقرأ عمود «الصف» إن وُجد ويطابقه بالهيكل؛ وإلا يستعمل الصف المختار
  وقت الرفع. ويظل قابلًا للتغيير لكل سطر في جدول المراجعة.
- **التكرار**: ينبّه على الاسم المسجّل في الصف نفسه هذا العام، ويتخطّاه افتراضيًا.
- **الصلاحيات**: الصف الافتراضي وكل صف في الملف يمران على `assertGradeAccess`.
  العبث بالصفحة لا يفيد — الرفض من الخادم.
- **الذرّية**: الحفظ في معاملة واحدة، فلا يبقى نصف كشف يُعاد رفعه فيتضاعف.
- **الحد الأقصى**: ٥٠٠ مخدوم في الملف الواحد، و٤ ميجابايت لما يُرفع إلى الخادم.
- **الرجوع التلقائي**: ملف PDF لم تُقرأ منه أسماء (طبقة نص مشوّهة أو بلا جدول)
  يُعاد قراءته ضوئيًا من الصورة بدل أن تنتهي المحاولة برسالة خطأ.

## صور المخدومين

الصورة تُحفظ في حاوية **خاصة** على Supabase Storage، ولا يُحفظ في قاعدة
البيانات إلا **مسارها** — لا الصورة نفسها.

```
المتصفّح  →  خادم الموقع  →  Supabase Storage
```

المتصفّح لا يتصل بـSupabase إطلاقًا: لا يرفع إليها ولا يقرأ منها ولا يحمل
مفتاحها. وعرض الصورة يمرّ من الخادم (`/api/children/<id>/photo`) بعد التحقق
من صلاحية المستخدم، فتبقى الحاوية خاصة ولا تُفتح للعموم.

### بنية المسار

```
child-photos/<معرّف المخدوم>/<اسم عشوائي>.jpg
```

اسم الملف عشوائي (`crypto.randomUUID`) لا اسم الملف الأصلي — فلا يكشف شيئًا
ولا يتصادم. ومعرّف المخدوم داخل المسار ليس ترتيبًا للعرض فقط: عند القراءة
يُرفض أي مسار محفوظ لا يطابق المخدوم المطلوب ولا يشير إلى الحاوية المضبوطة،
فسطرٌ عُبث به لا يقرأ ملفًا غريبًا.

**ومسار الصورة لا يُقبل من المتصفّح أبدًا** — يُقرأ من قاعدة البيانات بعد
التحقق من الصلاحية، وإلا لأمكن طلب صورة مخدوم خارج النطاق بتمرير مسار عشوائي.

### التقدّم أثناء الرفع

شريط التقدّم يتبع البايتات الخارجة فعلًا من الجهاز (`XMLHttpRequest` و
`upload.onprogress`) — لا مؤقّتًا يتحرّك من تلقائه. ولذلك استُعمل
`XMLHttpRequest` بدل `fetch`: الأخير لا يعطي تقدّم الإرسال في المتصفّح.

وللأمانة: التقدّم يقيس الرحلة الأولى (الجهاز ← الخادم). أمّا الرحلة الثانية
(الخادم ← Supabase) فلا يمكن رصدها من المتصفّح، فلا تُزوَّر بنسبة وهمية:
تتغيّر الرسالة إلى «جارٍ الحفظ في الأرشيف…» حتى يؤكّد الخادم النجاح فعلًا.
والصورة تُصغَّر في المتصفّح قبل الرفع (حدّه ١٢٠٠ بكسل)، فالرحلة الثانية أجزاء
من ثانية.

### القصّ قبل الرفع وعرض الصورة

عند اختيار صورة يُفتح إطار قصٍّ **دائري** — لأن الصورة تُعرض دائرية في كل
مكان، فما يراه المستخدم هنا هو ما سيراه بعد الحفظ تمامًا. يسحب ليحرّك، ويقرّب
بإصبعين أو بعجلة الفأرة أو بالشريط، والصورة لا تصغر عن ملء الإطار فلا ينتج
قصٌّ نصفه فراغ.

**ولا تُرفع إلا البايتات المقصوصة**: القصّ يقع قبل الرفع لا بعده.

والضغط على صورة محفوظة يفتحها بالحجم الكامل: تكبير بالنقر المزدوج وبإصبعين
وبالعجلة، وإغلاق بزرّ الإغلاق أو بالخلفية أو بمفتاح Escape أو بسحبها لأسفل.

### المعالجة قبل الرفع

الصورة الأصغر من ٩٠٠ كيلوبايت وضمن الأبعاد **لا تُمسّ** — فلا تخسر جودةً
بإعادة ترميز لا داعي لها. وما فوق ذلك يُصغَّر مرة واحدة من الأصل إلى ١٢٠٠
بكسل ويُرمَّز JPEG بجودة ٠٫٨٥ (نحو ١٥٠ كيلوبايت لصورة وجه). ويُملأ البياض
تحت الصور الشفافة قبل الترميز حتى لا تسودّ خلفيتها.

والتحقق من نوع الصورة يقع على **توقيع البايتات** لا على ترويسة
`Content-Type`: الترويسة يكتبها المرسِل، فملفٌ تنفيذي يُسمّى `.jpg` يمرّ لو
اكتُفي بها.

### تغيير الصورة

بالترتيب، ولا تُحذف القديمة إلا بعد أن تأمن الجديدة:

1. تُرفع الجديدة. لو فشلت، لم يتغيّر شيء والقديمة في مكانها، وتُعاد المحاولة.
2. يُحدَّث السجل. لو فشل، تُحذف الجديدة فورًا فلا تبقى صورةً يتيمة.
3. تُحذف القديمة. وفشل هذه الخطوة تنظيفٌ ناقص لا أكثر، فلا يُسقط العملية.

وعند إزالة الصورة يُفرَّغ السجل أولًا ثم يُحذف الملف: لو فشل الحذف بقي ملفٌ
زائد لا أكثر، أمّا العكس فيترك سجلًا يشير إلى صورة غير موجودة. وحذف المخدوم
يحذف صورته أيضًا، بعد حذف السجل لا قبله.

| `SUPABASE_SECRET_KEY` | مفتاح الخادم السري — **لا يُوضع في `NEXT_PUBLIC_*` ولا يُستورد في مكوّن عميل** |

```bash

```

يرفع صورة اختبار صغيرة ثم ينزّلها ثم يحذفها، ويطبع النتيجة — بلا إظهار أي
مفتاح. وصفحة **الإعدادات** تعرض الحالة كذلك: هل المفتاح صحيح، وهل الحاوية
موجودة، **وهل ما تزال خاصة** — فتحويل الحاوية إلى عامة ضغطةٌ في لوحة Supabase
لا أثر لها في الكود، ولو مرّت صامتة لانكشفت صور المخدومين لمن يعرف الرابط.

## التواريخ والأعمار

تاريخ الميلاد ليس لحظة بل **يومًا في التقويم**: «٢٠ سبتمبر ٢٠١٠» هو نفسه في
دمنهور وفي أي مكان. ولو عومل كلحظة تحوّل إلى «١٩ سبتمبر ٧:٠٠ م» على خادم
متأخّر عن UTC، فظهر اليوم ناقصًا واحدًا وقد نقص العمر سنةً كاملة حول يوم
الميلاد.

فالقاعدة في `src/lib/dates.ts` واحدة لا تُخرق: **يُخزَّن اليوم عند منتصف ليل
UTC، ويُقرأ بدوالّ UTC وحدها.**

- **الإدخال** ثلاث خانات: يوم / شهر / سنة. السنة تُكتب رقمًا مباشرة — منتقي
  المتصفّح يفتح على الشهر الحالي، فمن أراد مولودًا سنة ٢٠١٣ تنقّل عبر مئة
  وخمسين شهرًا.
- **التحقق** على الواجهة وعلى الخادم معًا: اليوم موجود فعلًا في شهره
  (٣١ فبراير مرفوض، و٢٩ فبراير مقبول في الكبيسة وحدها)، وليس في المستقبل.
- **العمر** سنواتٌ مكتملة تُحسب عند كل عرض، لا فرق بين السنتين: المولود في
  ٢٠ سبتمبر ٢٠١٠ يبقى ابن ١٥ يوم ١٩ سبتمبر ٢٠٢٦، ويصير ابن ١٦ يوم ٢٠ سبتمبر.
- **عيد الميلاد** في ٢٩ فبراير يُحتسب في آخر يوم من فبراير في السنوات غير
  الكبيسة.

## إحصائيات الحضور ونقاطه

```
نسبة الحضور = الحضور المسجَّل ÷ السجلات المسجَّلة × ١٠٠
```

**واليوم الذي لم يُفتح له اجتماع لا يدخل الحساب ولا يُحسب غيابًا.** الاجتماع
يُفتح صراحةً بضغطة، فالخدمة لا تُقاس بأيام لم تُسجَّل، ولا تنخفض النسبة لأن
أحدًا نسي أن يفتح الكشف. والصف الذي لا سجل له يظهر «—» لا «٠٪»: فرقٌ بين
«لا نعرف» و«صفر».

المستويات أربعة: **المخدوم** (في صفحته) و**الصف** و**المرحلة** و**الخدمة**.

ولا يُعرض مستوًى إلا إذا كان نطاق المستخدم يغطّيه **كاملًا**: نسبةُ مرحلةٍ
محسوبةٌ من صفٍّ واحد ليست نسبة المرحلة، وعرضها تضليل. فالخادم المكلّف بصف
يرى صفّه، وأمين المرحلة يرى مرحلته، وأمين الخدمة يرى الخدمة.

وكل الأعمدة بلون واحد لأنها تقيس الشيء نفسه وتُقارَن بالمقدار؛ ألوانٌ مختلفة
كانت ستوحي بهويات لا وجود لها. والنسبة مكتوبة على كل عمود، فالقراءة لا تتوقّف
على تمييز لون ولا على تقدير طول.

### النقاط — اختيارية

تُفعَّل من **الإعدادات ← نقاط الحضور** (لمسؤول النظام وحده)، وقيمة النقطة
قابلة للضبط لا مثبَّتة في الكود.

**والنقاط تُحسب من سجلات الحضور ولا تُخزَّن معها.** فتعطيل النظام لا يمسّ
سجلًا واحدًا، وتفعيله لاحقًا يحسب النقاط بأثر رجعي من السجلات الموجودة. وعند
التعطيل تختفي كل واجهة النقاط ويسير الحضور كما كان.

## الحذف بالضغط المطوّل

الضغط المطوّل (نصف ثانية) على أي عنصر يكشف زرّ الحذف، ثم يُطلب تأكيد. ثلاث
خطوات لفعلٍ لا رجعة فيه، وهي في محلّها — **والضغط المطوّل نفسه لا يحذف شيئًا**.

- **لا تُفتح اللوحة إن تحرّك الإصبع** أكثر من عشر بكسلات: التمرير في قائمة
  طويلة لا يجوز أن ينتهي بنافذة حذف.
- **على الحاسوب** يفتحها الزرّ الأيمن كذلك، وتبقى أزرار الحذف الظاهرة كما هي.
- تعمل على: المخدومين، والمستخدمين، والمراحل والأقسام والصفوف، واجتماعات
  الحضور.
- لا تظهر لمن لا يملك صلاحية الحذف — **والخادم يتحقق ثانيةً على كل حال**،
  فالإخفاء للراحة لا للأمان.

## النشر على Vercel

المشروع جاهز للنشر على Vercel، لكنه يحتاج قاعدة بيانات PostgreSQL مستضافة — **لا يمكن استخدام ملف قاعدة بيانات محلي على Vercel** لأن نظام الملفات هناك للقراءة فقط ومؤقت.

**١. أضف قاعدة بيانات**

من لوحة تحكم مشروعك على Vercel: تبويب **Storage** ← **Create Database** ← اختر **Neon** أو **Prisma Postgres** (كلاهما له خطة مجانية). بعد الربط يضيف Vercel متغيّر `DATABASE_URL` تلقائيًا للمشروع.

**٢. أضف مفتاح الجلسات**

من **Settings** ← **Environment Variables** أضف:

| المتغيّر | القيمة |
|---|---|
| `AUTH_SECRET` | نص عشوائي طويل — ولّده بـ `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |

**٣. أعد النشر**

من تبويب **Deployments** اضغط **Redeploy** على آخر نشر (مع إلغاء تفعيل خيار الكاش إن وُجد).

أمر البناء `npm run build` يطبّق ترحيلات قاعدة البيانات ويهيّئ الهيكل التنظيمي تلقائيًا في أول نشر، فلا حاجة لأي خطوة يدوية على قاعدة البيانات.

> ترحيلات Prisma تُنفَّذ عبر **الاتصال المباشر (unpooled)** ومع تعطيل قفل الترحيلات، لأن القفل لا يعمل عبر الـpooler وقد يتسرّب فيوقف كل نشرة تالية. التطبيق وقت التشغيل يظل على الاتصال المُجمَّع. يتكفّل `scripts/db-deploy.mjs` بذلك تلقائيًا — لا يحتاج أي إعداد إضافي.

> ⚠️ بعد أول دخول ناجح، **غيّر كلمة مرور حساب `admin` فورًا** من الإعدادات ← المستخدمون، لأنها منشورة في هذا الملف.

## حل المشكلات الشائعة

**بعد تسجيل الدخول يرجعني للصفحة نفسها / لا يفتح شيء**

كان هذا يحدث عند تشغيل نسخة الإنتاج والدخول عليها من عنوان غير `localhost` عبر HTTP عادي (مثل فتح الموقع من الموبايل على `http://192.168.x.x:3000`): كان كوكي الجلسة يُرسَل بخاصية `Secure` فيرفضه المتصفح على اتصال غير مشفّر، فتضيع الجلسة ويعود المستخدم لصفحة الدخول. **تم إصلاحه** — صار التطبيق يضبط `Secure` حسب بروتوكول الطلب الفعلي (`x-forwarded-proto`)، فيعمل على HTTP داخل الشبكة المحلية وعلى HTTPS في الإنتاج.

**«تعذّر تشغيل التطبيق» على الموقع المنشور**

معناها أن `DATABASE_URL` أو `AUTH_SECRET` غير مضبوط في بيئة النشر، أو أن قاعدة البيانات غير متاحة. راجع قسم [النشر على Vercel](#النشر-على-vercel) أعلاه. (كان السبب الأصلي هو محاولة استخدام SQLite كملف على القرص، وهو ما لا يعمل على Vercel إطلاقًا — وقد تم تحويل المشروع إلى PostgreSQL.)

**شاشة بيضاء أو خطأ عند فتح أي صفحة بعد استنساخ المشروع**

ملف `.env` غير مرفوع مع المستودع (لأنه يحتوي أسرارًا)، فبدونه لا يعمل التطبيق. شغّل:

```bash
npm run setup
```

يُنشئ `.env` بمفتاح `AUTH_SECRET` عشوائي، يطبّق ترحيلات قاعدة البيانات، ويعبّئ البيانات الأولية (يتخطى الموجود مسبقًا). التطبيق الآن يعرض رسالة خطأ عربية واضحة بدل الشاشة البيضاء إن نقص أي إعداد.

**تسجيل الدخول يرفض البيانات الصحيحة** — قاعدة البيانات غالبًا فارغة؛ شغّل `npm run db:seed`.

**فشل النشر بـ`P1002: Timed out trying to acquire a postgres advisory lock`**

قفل الترحيلات (`pg_advisory_lock`) لا يعمل عبر اتصال Neon المُجمَّع، بل **يتسرّب**: ينتهي انتظار العميل بعد عشر ثوانٍ بينما يبقى خادم خلفي في الـpooler ماسكًا للقفل، فتفشل كل محاولة تالية حتى على الاتصال المباشر.

تم إصلاحه في `scripts/db-deploy.mjs`: الترحيلات تمر على الاتصال المباشر **ومع تعطيل القفل** (`PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK`). القفل وظيفته منع تزامن عمليتي ترحيل، وهو تزامن لا يحدث هنا لأن Vercel ينفّذ بناءً واحدًا في المرة.

**فشل النشر بـ`type "Role" already exists` أو `P3018`**

قاعدة البيانات تحتوي جداول من ترحيل قديم لم يعد موجودًا. إن لم تكن بها بيانات حقيقية بعد، أفرغها من محرر SQL في Neon ثم أعد النشر:

```sql
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
```

⚠️ هذا يمسح كل شيء — لا تستخدمه بعد أن تبدأ الخدمة في إدخال بياناتها الفعلية.

## القرارات التصميمية ولماذا

عند تعارض متطلبين اخترت الحل الأكثر عمليةً وأمانًا وقابلية للصيانة:

- **PostgreSQL مستضافة بدل SQLite:** بدأ المشروع بـSQLite لبساطتها، لكن النشر على Vercel أثبت أنها غير صالحة هناك: نظام الملفات للقراءة فقط ومؤقت، وكل طلب قد يعمل على خادم مختلف، فلا تُحفظ أي كتابة. PostgreSQL المستضافة هي الخيار الصحيح لأي نشر سحابي.
- **تشغيل الترحيلات والتعبئة الأولية داخل أمر البناء:** (`prisma migrate deploy && prisma db seed && next build`) حتى لا تحتاج خطوة يدوية بعد كل نشر. التعبئة محميّة بشرط: تعمل فقط إذا كانت قاعدة البيانات فارغة تمامًا، فلا تُعيد إنشاء بيانات حذفها الخدام لاحقًا.
- **مصادقة مخصّصة بدل NextAuth:** النسخة المتوافقة مع React 19 من NextAuth كانت تُفشل تثبيت الحزم (عطل معروف في محلل تبعيات npm مع هذا الإصدار)؛ حل JWT+كوكي httpOnly مباشر أبسط وأكثر قابلية للتتبع لتطبيق بحجم كهذا، مع نفس ضمانات الأمان (تواقيع موقّعة، httpOnly، secure في الإنتاج).
- **Server Actions بدل REST API منفصل:** يقلّل الكود المكرر (لا حاجة لـ fetch + API route لكل نموذج) مع إبقاء كل التحقق (`zod`) وفحص الصلاحيات على الخادم دائمًا.
- **جلسات الحضور اليومية + الافتقاد الشهري:** يعكس تمامًا الجدولين الفعليين في ملف بيانات الخدمة المرفق (شبكة شهرية للحضور بعدة أعمدة لكل شهر، وعمود واحد شهري للافتقاد).

## ما هو منفَّذ فعليًا

لا توجد شاشات "قريبًا" في هذا المشروع — كل ما يظهر في الواجهة يعمل فعليًا ومتصل بقاعدة بيانات حقيقية:

- تسجيل دخول/خروج بجلسات موقَّعة وحماية كل المسارات.
- صلاحيات مبنية على (الدور + نطاق التكليف) مطبَّقة في طبقة البيانات لا في الواجهة.
- إدارة كاملة (إضافة/تعديل/حذف/تعطيل) للمراحل والأقسام والصفوف، والمخدومين وأرقام تليفوناتهم المتعددة، والمستخدمين وتكليفاتهم.
- استيراد كشوف المخدومين من Excel و CSV و Word و PDF والصور، بمراجعة قبل الحفظ وقالب جاهز للتنزيل.
- صور المخدومين مخزَّنة في حاوية خاصة على Supabase Storage، ترفعها الواجهة بتقدّم حقيقي وتعرضها عبر الخادم وحده.
- تسجيل حضور فعلي لكل جلسة بثلاث حالات (حاضر/غائب/بعذر) مع تنقل بين التواريخ وسجل جلسات سابقة.
- متابعة افتقاد شهرية فعلية مع ملاحظات لكل مخدوم.
- تقويم أعياد ميلاد حقيقي مبني على بيانات المخدومين الفعلية، مع تمييز الشهر الحالي واليوم نفسه.
- لوحة تحكم بإحصائيات حقيقية (لا بيانات وهمية): عدد الصفوف/المخدومين، نسبة الحضور والافتقاد الفعلية هذا الشهر، آخر النشاطات، أقرب أعياد الميلاد.
- بحث فوري، حالات فارغة/تحميل/خطأ مصمَّمة لكل شاشة بيانات.
- وضع داكن كامل مصمَّم خصيصًا (ليس عكس ألوان).
- Responsive حقيقي من 360px إلى الشاشات الكبيرة: جداول تتحول لبطاقات على الهاتف، تنقل سفلي على الهاتف وشريط جانبي على الشاشات الكبيرة.

تم اختبار كل هذه التدفقات فعليًا عبر متصفح Chromium حقيقي (Playwright) على أبعاد سطح المكتب والهاتف، بثلاثة أدوار مختلفة، بدون أي أخطاء في الـ console.
